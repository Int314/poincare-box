# ポアンカレの箱 — 仕様

## 1. 主題

**ポアンカレの回帰定理**（Poincaré recurrence theorem）: 有限体積・エネルギー保存の力学系は、確率1で初期状態の任意の近傍に無限回戻る。

> ⚠️ **ポアンカレ予想**（ペレルマンが証明した位相幾何の問題）とは別物。サイトのコピーで混同しないこと。

これを「箱の中の100個の粒子が全部左半分に集まる瞬間」として実装する。熱力学第二法則は統計的な法則にすぎないので、エントロピーの自発的減少は禁止されていない。ただ待てる人がいないだけ。

- 全粒子が左に集まる確率: 2⁻¹⁰⁰ ≒ 1/1.27×10³⁰
- 30秒に1回の観測での期待待ち時間: **約 1.2×10²⁴ 年**（宇宙年齢の約8.7兆倍）

## 2. 凍結条項（最重要）

粒子配置は**保存されていない**。`SEED` と `tick` から毎回導出される。したがって以下を変更すると**過去の歴史がすべて書き換わり**、記録された最高記録・初出日時・突破した壁がすべて無意味になる。

`public/core.js` の以下は**変更禁止**:

| 対象 | 値 |
|---|---|
| `SEED` | `poincare-box-v1` |
| `N`（粒子数） | `100` |
| `TICK_MS` | `30000` |
| `EPOCH_MS` | `2026-08-13T00:00:00Z` |
| ハッシュ入力の形式 | `` `${SEED}:${tick}` `` |
| ハッシュ関数 | SHA-256 |
| ビットの取り出し | h0,h1,h2 の32bit × 3 + h3 の上位4bit = 先頭100ビット。ビットが 1 の粒子が左半分 |

バグを見つけた場合も**修正してはいけない**。`SEED` を変えて「実験のやり直し」として過去の記録を破棄することを明示する以外に道はない。

### 凍結対象ではないもの（自由に変えてよい）

- 確率の壁のはしご（`WALL_EXPONENTS`）— `records` には `k` がそのまま入るので、刻みを変えても記録は失われない
- 見た目（色・レイアウト・アニメーション・コピー）
- 集計スキーマ（`daily` の列追加など。`records` から再構築できる）

### N=100 の根拠

粒子数で難易度が全部決まる。N=50 だと本命の期待待ち時間が10.7億年で**宇宙年齢より短くなり**、「絶対に不可能」の説得力が消える。N=100 で初めて「宇宙を8兆回繰り返しても足りない」になる。

部分記録（左に何個寄ったか）の伸び方も N=100 が最適で、初日に65個まで一気に到達したあと対数的に固まる。実測値（`node tools/verify.mjs`）:

| 経過 | 最高記録 |
|---|---|
| 1日 | 65個 |
| 1週間 | 68個 |
| 1ヶ月 | 70個 |
| 3ヶ月〜191日 | 72個 |

「100個中72個も左に寄っているのにゴールは絶望的に遠い」という体感を作るのが狙い。

### なぜ物理シミュレーションではないのか

「粒子を実際に飛ばして数えればいいのでは」という案は 2026-08-15 に実測で検証し、**却下した**。N=20（全部左が約100万分の1）に縮小して各1000万サンプルを走らせた結果:

| 方式 | 「全部左」の回数（期待値 9.5） |
|---|---|
| 連続体ビリヤード・速度が無理数比 | 13 回 ✓ |
| 同・速度を 0.05 刻みに丸める | **0 回**（最高 16/20、k は 13 通りのみ） |
| 同・速度 8 種類から選ぶ | **0 回**（最高 15/20） |
| 可逆格子気体 HPP・希薄 | 4 サンプルに 1 回（k は 4 通りのみ） |
| 可逆格子気体 HPP・100粒子 | 混合はするが leftCount の平均が 50 でなく **56.6 に固定** |

原因はどれも同じで、**決定論的な有限系には必ず保存量と巡回構造があり、それが 2⁻¹⁰⁰ という確率を壊す**。速度が単純な比だと系が短周期に落ちて「全部左」が稀ではなく到達不可能になり、HPP は行・列ごとの運動量保存で初期の左寄りを永久に記憶してエルゴード的にならない（400万歩まわしても平均が動かない）。物理エンジン（Rapier 等）は反発係数 < 1・減衰・sleep・非可逆な逐次インパルス法のため、さらに不適切。

ハッシュ方式の価値は**力学を持たないこと**そのものにある。保存量も巡回も時間相関もないので 2⁻¹⁰⁰ が厳密に出る。理想気体のモデルとしては、実際のシミュレーションよりハッシュのほうが忠実。

なお、ポアンカレの回帰定理が保証するのは「**初期状態**への回帰」であって「あらゆる状態を訪れる」ことではない（後者はエルゴード性で、遥かに強い仮定）。本サイトが主張する「全部左に到達する」は厳密には回帰定理ではなく二項分布の裾であり、この乖離は既知の妥協。`index.html` の「粒子の動きは演出です」で開示している。

## 3. 確率の壁（副目標）

記録 `k` をその希少度に翻訳してバッジ化する。「77個」より「1億分の1の壁を突破」のほうがポストされやすい。

| 壁 | 必要な k | 実際の希少度 |
|---|---|---|
| 10² | 63 | 1/166 |
| 10³ | 66 | 1/1,117 |
| 10⁴ | 69 | 1/10,920 |
| 10⁵ | 72 | 1/158,993 |
| 10⁶ | 74 | 1/1,199,499 |
| 10⁷ | 76 | 1/1.10×10⁷ |
| 10⁹ | 80 | 1/1.79×10⁹ |
| 10¹² | 85 | 1/4.14×10¹² |
| 10¹⁶ | 90 | 1/6.53×10¹⁶ |
| 10²¹ | 95 | 1/1.60×10²² |
| 10³⁰ | **100（本命）** | 1/1.27×10³⁰ |

実測（`node tools/verify.mjs`）では公開初日に 1/11、1週間で 3/11、3ヶ月で 4/11 が埋まる。以後は 191日走らせても 4/11 のまま動かない。

## 4. アーキテクチャ

```
public/core.js   凍結コア。Worker とブラウザが共有する唯一の実装。
                 静的配信もされるので第三者が全履歴を検証できる。
src/index.js     Worker。/api/state（集計＋追いつき）と /api/at（純粋計算）。
db/schema.sql    D1。集計結果だけを持つ（配置は持たない）。
public/app.js    Canvas 描画と観測演出。配置はブラウザ自身が計算する。
tools/verify.mjs 検証ツール。node:crypto との一致確認と走査シミュレーション。
```

### 遅延生成（lazy tick）

Cron Trigger の最短間隔は1分なので30秒刻みには使えないが、配置は tick から決定論的に導出されるので**そもそも定期実行が要らない**。

- `/api/state` へのアクセス時に `last_tick` から現在 tick までを走査して集計
- 誰も見に来なくても日次 Cron（00:17 JST）が追いつかせる
- 実測: 1日ぶん(2,880 tick)の追いつきが **0.9ms**、1年ぶんでも 0.32秒

「観測されたときに初めて30秒に1文字だったことになる」という挙動になり、主題（観測されるまで配置は確定しない）と整合する。

### 同期版 SHA-256

`crypto.subtle` は非同期なので、数千 tick を一括再現するときに await 連打になる。`core.js` は単一ブロック専用の同期実装を持つ（入力は常に56バイト未満）。`node:crypto` との一致は 20,010 tick 分をテストで確認済み。

### 並行実行の安全性

`catchUp()` は集計値を**絶対値で書き戻す**（インクリメントしない）。ただしそれだけでは足りない。`last_tick` と `records`/`daily` を別々のクエリで読むと、その隙間に他のリクエストが書き戻したぶんの上にもう一度同じ tick を加算してしまい、二重カウントが**固定化する**。

これは理論上の話ではなく、実際に本番で 6 回ぶん膨らんだ（2026-08-15 に集計を作り直して解消。配置はハッシュから導出できるので、最高記録・初出 tick・出現回数はすべて同一の値で復元された）。

対策として、3 つの読み取りを 1 回の `env.DB.batch()`（単一トランザクション）にまとめ、同一断面を取る。`daily` の絞り込み範囲だけは先読みした `last_tick` を使うが、`last_tick` は単調増加なので必要な範囲を必ず含む。修正後は 120 並列 + 実トラフィック 1 日で超過ゼロを確認済み。

## 5. データモデル

| テーブル | 内容 | サイズ |
|---|---|---|
| `meta` | `last_tick` のみ | 1行 |
| `records` | k ごとの初出 tick と累計回数 | 最大101行 |
| `daily` | 日次の最高記録・観測数・エントロピー減少回数・最小エントロピー（日境界は JST） | 1行/日 |

永久に動かしても D1 の無料枠に触れない。

## 6. 画面

- **箱**: 100粒子が自由運動（粒子同士は等質量の弾性衝突。運動量・運動エネルギーを厳密に保存する演出で、判定には非関与）→ 30秒ごとに整列（900ms）→ 確定の閃光と左右の色分け → 2.6秒保持 → 再び自由運動
- **統計**: 総観測回数 / 最高記録とその希少度 / 突破した壁
- **本日のログ**: 50からの偏りを上下の棒で描くスパークライン（上=左寄り）。1日2,880観測ぶんの幅で固定して進行度が見える
- **タイムマシン**: 任意の日時の配置をブラウザ側で再計算。`?t=<tick>` で固定URLになるので、記録が出た瞬間を共有できる
- **エントロピー**: S = ln C(N,k) / ln C(N,50) で正規化（1.0=最も乱雑、0=完全に整列）

粒子の動きは演出であり、判定は30秒ごとの独立サンプリングであることをサイト上で明示する。

## 7. 運用

```bash
npm run verify      # 決定論と SHA-256 一致の検証
npm run dev         # ローカル起動
npm run db:local    # ローカル D1 にスキーマ適用
npm run db:remote   # 本番 D1 にスキーマ適用
npm run deploy
```

デプロイ前に `wrangler d1 create poincare-box-db` して `wrangler.jsonc` の `database_id` を差し替える。
