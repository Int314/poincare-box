# ポアンカレの箱 — 設計の理由

主題はポアンカレの**回帰定理**。ペレルマンが証明した**ポアンカレ予想**とは別物なので、コピーで混同しない。

## 凍結条項（最重要）

粒子配置は保存しておらず、`SEED` と `tick` から毎回導出する。次を変えると過去の歴史がすべて書き換わり、最高記録・初出日時・突破した壁が無意味になる。

`public/core.js` の `SEED` / `N` / `TICK_MS` / `EPOCH_MS` / ハッシュ入力の形式 / ハッシュ関数 / ビットの取り出し順は**変更禁止**。
バグを見つけても修正しない。直すなら `SEED` を変えて「実験のやり直し」として過去の記録を破棄すると明示する以外にない。

自由に変えてよいもの：壁のはしご（`WALL_EXPONENTS`。`records` には `k` がそのまま入る）、見た目とコピー、集計スキーマ（`records` から再構築できる）。

### N=100 の根拠

N=50 だと期待待ち時間が約 10.7 億年で宇宙年齢より短くなり、「絶対に不可能」の説得力が消える。N=100 で初めて「宇宙を 8 兆回繰り返しても足りない」になる。部分記録の伸び方も N=100 がよく、初日に 65 個前後まで伸びたあと対数的に固まる（`node tools/verify.mjs` で再現できる）。

### 物理シミュレーションにしない理由（実測で却下済み）

N=20 に縮めて各 1000 万サンプル（「全部左」の期待値 9.5 回）で比べた：

- 連続体ビリヤード・速度が無理数比：13 回（唯一まともだが、速度を離散化した途端に 0 回）
- 速度を離散化：0 回（k の取りうる値が十数通りに縮退）
- 可逆格子気体 HPP：leftCount の平均が 50 でなく 56.6 に固定（運動量保存で初期の偏りを永久に記憶する）

決定論的な有限系には必ず保存量と巡回構造があり、それが 2⁻¹⁰⁰ を壊す。物理エンジンは反発係数 < 1・減衰・sleep のためさらに不適切。ハッシュ方式は力学を持たないので 2⁻¹⁰⁰ が厳密に出る。

なお「全部左に到達する」は厳密には回帰定理ではなく二項分布の裾で、この乖離は既知の妥協。`index.html` の「粒子の動きは演出です」で開示している。

## 実装上の理由

- **定期実行を持たない**：Cron の最短は 1 分で 30 秒刻みに使えないが、配置は tick から導出できるので `/api/state` のアクセス時に追いつけば足りる（誰も来ない日は日次 Cron が追いつかせる）
- **同期版 SHA-256**：`crypto.subtle` は非同期で、数千 tick を一括再現すると await 連打になる。`node:crypto` との一致は `tools/verify.mjs` が CI で検証する
- **追いつきの並行実行**：`catchUp()` は集計値を絶対値で書き戻すが、それだけでは足りない。`last_tick` と `records`/`daily` を別クエリで読むと、その隙間に他のリクエストが書いたぶんに同じ tick を二重加算して固定化する。3 つの読み取りは 1 回の `env.DB.batch()` で同一断面を取る。万一膨らんでも集計はハッシュから作り直せる
